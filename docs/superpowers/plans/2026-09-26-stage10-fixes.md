**Architecture:** Two structural moves, and everything else is local.
- **Stage 10 discovery is judged per track, not per artist.**
  - A new append-only cache keeps each Spotify search result's `artists` (name, id) and `duration_ms`.
  - Every discovery pick then passes a track gate: genre match, lead or remixer credit, drag co-credit, pinned artist id, live, length and veto.
  - Supply comes in this order: hand-named acts, then SJ's own artists' unplayed tracks, then gated strangers, then more of SJ's own tracks, then the known pool. That is SJ's decision 3.
- **The export's coverage bounds every "now".**
  - Stage 3 reads export rows only.
  - Every `max(month)` window anchors on one definition, `config.ANALYSIS_HORIZON_SQL`.
  - Polled plays still repair credits and still count as Stage 10 hours. They never enter trends, done-rates or window anchors.

**Tech Stack:** Python 3.12 in `.venv`, DuckDB over Parquet, the existing `playlists.Spotify` client (it has no delete verb), `enrich.Throttled`, and `consolidate.find_playlist`/`read_playlist` for one read-only lookup. No new dependencies.

## Global Constraints

- Every Python invocation uses `.venv/bin/python`. Quote the repo path: `"/Volumes/Dock Storage/Projects/spotify-trend-analysis"`.
- DuckDB SQL over pandas wherever the two are equivalent.
- **Every Parquet write has a total order.** That means `ORDER BY ALL`, or a key that is provably unique.
- **Caches are append-only, fsynced JSONL, and store only real answers:**
  - an HTTP 200, including an empty 200;
  - never a failure.
- **Legacy empty entries** written before a status was recorded are re-asked **once**, and are then final. That one-time spend is the only exception to "only spend on the never-seen".
- **Throttling.** MusicBrainz and ListenBrainz use `Throttled(MB_MIN_INTERVAL)` (1.1 s). Spotify requests are spaced ≥0.25 s and honour 429 `Retry-After`.
- **No playlist is ever deleted or unfollowed.**
  - Stage 10 writes only to the two IDs in `data/running_state.json`, or to an exact-name or alias match (Task 10).
  - **Stage 8 runs `--dry-run` only.** The live indie frontier playlist holds a hand-added track (Dexter and The Moonrocks, "Freakin' Out") that a replace would remove.
- **No playlist IDs, tokens or `.env` contents in any tracked file.** `.claude/settings.json` denies `.env` reads; leave it.
- **Tests are offline plain-assertion scripts in `tests/`,** run from the repo root. They use synthetic DuckDB tables and fake `Throttled`/`Spotify` objects, never the network: `for t in tests/test_*.py; do .venv/bin/python "$t" || break; done`.
- **Worktrees have no gitignored files:** no `data/`, `.cache/`, `.env`, `running_overrides.csv` or `artist_overrides.csv`.
  - Implementation and unit tests happen in worktrees.
  - Every run against real data (Tasks 20–24) happens in the main checkout after merge.
- **Branch:** `stage10-fixes` off `main`. PRs need SJ's approval; plain merges don't.
  - If the git-guard hook denies a write ("another git write is in progress"), wait and retry.
  - Never remove a lock.
- **Never introduce a printable-delimiter join of artist names.** New artist lists are DuckDB `LIST`s or JSON arrays. `0x1f` (`poll.ARTIST_SEP`) is the only permitted string separator.

### Task 2: Seeds and candidate ranking (evaluation C1, C6; re-run anomaly 8)

**Files:** `running.py` `cluster_candidates` 324-379, new `cluster_seed_artists`; `config.py`; new `tests/test_running_discovery.py`.

**Change:**
- **C1, the seed query.** It is extracted into `cluster_seed_artists(con, label, vetoes) -> list[dict]` (`mbid`, `artist_name`, `score`, `hours`), which Task 8 also uses:

```sql
WITH a AS (SELECT artist_name, any_value(mbid) AS mbid
           FROM artist_tags WHERE mbid IS NOT NULL GROUP BY 1),   -- ONE row per artist
per_name AS (
    SELECT c.artist_name, a.mbid, sum(k.score) AS score, sum(k.hours) AS hours
    FROM known_pool k
    JOIN track_credits c USING (spotify_track_uri)
    JOIN a ON a.artist_name = c.artist_name
    JOIN artist_clusters ac ON ac.artist_name = c.artist_name
    WHERE k.cluster = ? AND ac.cluster = ?
    GROUP BY 1, 2
)
SELECT mbid, arg_max(artist_name, score) AS artist_name,
       sum(score) AS score, sum(hours) AS hours
FROM per_name GROUP BY mbid                                  -- Skrillex/SKRILLEX -> one seed
HAVING sum(hours) >= {config.RUN_MIN_SEED_HOURS}
ORDER BY score DESC, mbid
```

### Task 17b: Enrich — `NONE`, an override that un-resolves a wrong match (W4; research-pass finding)

**The gap.** A tags-only row (blank `mbid`) replaces an artist's genres but cannot un-resolve them. `apply_overrides` skips it (`enrich.py:335-341`), `purge_stale_overrides` only evicts `source = 'override'` records, and `todo` never re-searches a cached name — so a wrong auto-match made *before* the row was added stays in the cache with its MBID, and `apply_override_tags` hangs the hand tags on that wrong MBID.
